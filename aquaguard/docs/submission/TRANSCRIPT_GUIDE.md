# Recovering and preserving genuine execution evidence

The user has not supplied an original transcript. A reconstructed requirements document is useful context but cannot replace the guide's evidence of one-prompt execution.

## Recovery

Search the original account/tool's available history, previously exported conversations, saved prompt files, team records and explicitly retained logs. Use only records the project owner can access. Preserve original files, dates and identifiers. A plan or commit message mentioning a master prompt is a lead, not the missing transcript itself.

If only part of the history is recovered, label it a partial export and identify the missing interval. Do not merge unrelated conversations into an apparent continuous execution. Screenshots and Git history can corroborate events but cannot prove absent dialogue. Do not recreate messages from memory as exact quotations.

## If no original record can be recovered

Submit the disclosure and reconstruction only if the organizer accepts them. The unsent clarification draft is in ORGANIZER_CLARIFICATION.md. If the organizer permits a fresh attempt, obtain its accepted starting state, deadline and scope first. A new execution does not retrospectively change the old history.

For a permitted fresh run, save the exact prompt before execution, its SHA-256, starting revision, real tool/model settings and the actual event export as it is produced. Record each genuine approval/continuation event and real deployment action. Include actual code diffs, command outcomes and final revision. Do not add extra substantive prompts while presenting the run as approval-only.

Use execution_record_template.json as an index of evidence files. It intentionally contains no events, dates, outcome or transcript. It is not an executable workflow, conversation export or simulated transcript. Preserve raw exports separately; disclose exact redactions and their reasons. Never expose credentials merely to make an export look complete.
